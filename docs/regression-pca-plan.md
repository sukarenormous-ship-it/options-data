> ต่อจาก `next-phase-plan.md` ซึ่งปิดครบทั้ง 5 งาน (A–E) แล้ว

## งาน F — บท "volatility surface ขยับด้วยกี่ทิศทาง"

**ไฟล์:** `statarb-pca-surface.html` + `tools/pca_figures.py` → `docs/pca-figures.json`

### คำถามที่บทต้องตอบ
กระดาน option ทั้งกระดาน (หลายร้อยสัญญา หลาย strike หลายอายุ) **จริง ๆ แล้วขยับด้วยตัวเลขกี่ตัว** — และ **จะรู้ได้ยังไงว่าทิศที่เจอเป็นของจริง ไม่ใช่ noise**

### โครง
1. ปัญหาตั้งต้น: จะ hedge กระดานทั้งกระดานยังไง ถ้ามันมี 300 สัญญาที่ขยับไม่พร้อมกัน
2. ย่อกระดานเป็นตาราง — เลือก bucket ตาม **moneyness ปรับด้วยอายุ** `ln(K/S)/√(T)` × **ช่วงอายุ** (ทำไมต้องปรับด้วย √T ไม่ใช้ `K/S` ดิบ)
3. PCA คืออะไรในภาษาคน (ลิงก์กลับ `math-part4` §1.4 ไม่สอนซ้ำ)
4. **ผลจริงจากคลัง** — PC1/PC2/PC3 คืออะไรในเชิงความหมาย (level / skew / term-structure) พร้อมภาพ eigenvector
5. 💎 **แก่นของบท: "84% ฟังดูดี แต่ของจริงกี่ทิศ"** — เกณฑ์ Marchenko-Pastur ที่ขนาดตัวอย่างจริง
6. เทียบกับเคส yield curve ในเล่มคณิต — ทำไมกระดาน option ถึง "สกปรก" กว่า
7. ❌ กับดัก: เปลี่ยนวิธีแบ่ง bucket แล้วคำตอบเปลี่ยนไหม (robustness check)
8. 🎓 เอาไปใช้: จาก 3 ทิศ สู่การ hedge / สร้างสัญญาณ

### ตัวเลขที่คำนวณได้จริง ⭐ (สำรวจไว้แล้ว — ตัวเลขจริงจากคลัง)

สำรวจด้วยตาราง 20 ช่อง (moneyness 5 ช่วง × อายุ 4 ช่วง) บน BTC · **ทั้งสองตลาดมีข้อมูลครบทั้ง 20 ช่อง ทั้ง 57 วัน ไม่มีช่องว่างเลย** · PCA บน correlation matrix ของ **การเปลี่ยนแปลง IV รายวัน** (56 วัน × 20 ช่อง)

| | PC1 | PC2 | PC3 | 3 ตัวแรกรวม |
|---|---|---|---|---|
| **Deribit** | 64.0% | 14.1% | 6.0% | **84.1%** |
| **OKX** | 63.8% | 12.5% | 6.4% | **82.7%** |

สองตลาดที่เก็บข้อมูลแยกกันได้ตัวเลขใกล้กันมาก — เป็นหลักฐานว่าโครงสร้างที่เจอไม่ใช่ artifact ของตลาดใดตลาดหนึ่ง

**แล้วนี่คือหมัดของบท:** ที่ขนาดตัวอย่างจริง (T=56, N=20 → q=0.357) เกณฑ์ Marchenko-Pastur ให้ขอบบนของ noise ที่ **λ⁺ = 2.552**

| | eigenvalue จริง (5 ตัวแรก) | เหนือเกณฑ์ noise |
|---|---|---|
| **Deribit** | 12.81 · **2.81** · 1.20 · 0.93 · 0.77 | **2 ทิศ** |
| **OKX** | 12.76 · **2.51** · 1.27 · 1.00 · 0.52 | **1 ทิศ** (PC2 = 2.51 เฉียด λ⁺ = 2.552 แบบหวุดหวิด) |

→ **"3 ทิศทางอธิบายได้ 84%" ฟังดูหนักแน่น แต่ที่ข้อมูล 56 วัน มีแค่ 1–2 ทิศที่แยกออกจากความสุ่มได้จริง — และสองตลาดยังตอบไม่ตรงกันด้วยซ้ำว่า PC2 นับหรือไม่นับ**

นี่คือวิทยานิพนธ์ของหนังสือทั้งเล่มปรากฏในหัวข้อใหม่พอดี และตรงกับผลของบท `statarb-signal-blending` (ค่ายก +8.3 จุด อยู่แค่เปอร์เซ็นไทล์ 62 ของสุ่ม) แบบคนละวิธีวัด

> ⚠️ ตัวเลขข้างบนเป็น **การสำรวจเบื้องต้น** — ขอบเขต bucket เป็นการเลือกเฉพาะกิจของรอบสำรวจ สคริปต์จริงต้องล็อกนิยาม bucket ไว้ในโค้ด และหัวข้อ 7 ต้องรายงานว่าเปลี่ยนนิยามแล้วคำตอบขยับแค่ไหน ห้ามเลือกนิยามที่ให้ผลสวยที่สุดแล้วรายงานอันเดียว

### เกณฑ์เสร็จ
อ่านจบแล้วรัน `pca_figures.py` กับข้อมูลตัวเองได้ · ตอบได้ว่า "ที่ข้อมูลเท่าที่ฉันมี ฉันมีสิทธิ์เชื่อกี่ factor" · ตัวเลขทุกตัวในบทมาจาก `pca-figures.json`

## งาน G — บท "รวมสัญญาณด้วยโมเดล ไม่ใช่ด้วยกฎ AND/OR"

**ไฟล์:** `statarb-logistic-meta.html` + `tools/logistic_figures.py` → `docs/logistic-figures.json`

### คำถามที่บทต้องตอบ
บท `statarb-signal-blending` จบลงด้วยผลว่า **การค้นหา 114 วิธีรวมแบบ AND/OR/vote/weight ไม่ได้เพิ่มมูลค่าเลย** — คำถามที่ค้างคือ *แล้วมีวิธีรวมที่ดีกว่านั้นไหม* บทนี้ตอบด้วยเครื่องมือมาตรฐานที่คลังยังไม่มี: **logistic regression**

### ทำไมต่อกันพอดี
`blending_figures.py` มีของครบอยู่แล้ว — ป้ายกำกับไบนารี (`|z[t+1]| < |z[t]|` สเปรดลู่เข้าจริงไหม) และตัวกรอง 4 ตัว บทที่แล้วใช้มันแบบ **ไบนารี** (ผ่าน/ไม่ผ่านเกณฑ์) ซึ่งทิ้งข้อมูลไปมาก — logistic regression ใช้ค่า **ต่อเนื่อง** ของสัญญาณเดียวกัน และให้ค่าที่ AND/OR ให้ไม่ได้: **ความน่าจะเป็น**

### โครง
1. ทำไมกฎ AND/OR ถึงทิ้งข้อมูล — `|z| = 1.49` กับ `|z| = 0.2` ถูกนับเหมือนกันหมด
2. จากเส้นตรงสู่ความน่าจะเป็น — logit / sigmoid (ต่อจาก linear regression ใน `math-part4` §2 โดยตรง)
3. อ่านผล logistic — coefficient แปลว่าอะไร (odds ratio) ต่างจาก OLS ยังไง
4. **meta-labelling** (López de Prado) — แยก "จะเข้าไหม" ออกจาก "จะเข้าเท่าไร" · คลังนับได้แค่ 3 ครั้ง และไม่เคยสอนจริง
5. วัดผลอย่างซื่อสัตย์ — ROC/AUC · **calibration curve** (โมเดลบอก 70% แล้วมันชนะ 70% จริงไหม) · walk-forward ไม่ใช่ k-fold (ลิงก์ `math-part11` §12.3)
6. 💎 เทียบกับบทที่แล้วตรง ๆ: logistic ชนะการค้นหา 114 วิธีไหม **และชนะ noise baseline เดียวกันไหม**
7. ❌ กับดัก: 4 ตัวแปรบน n วัน — DoF พอไหม (ลิงก์ `math-part11` บทที่ 14 → ใช้ Ridge/Lasso คุม)

### ตัวเลขที่คำนวณได้จริง ⭐
- ใช้ **ข้อมูล ป้ายกำกับ และ noise baseline ชุดเดียวกับ `blending_figures.py`** เป๊ะ ๆ (Write Once — import ซ้ำ ไม่คำนวณใหม่) เพื่อให้เทียบกันได้ตรง ๆ ว่า "โมเดล vs กฎ" ต่างกันจริงกี่จุด
- AUC และ calibration ของ logistic บน walk-forward
- **รันการค้นหาบน noise แบบเดียวกันซ้ำ** — logistic บนป้ายกำกับสุ่มได้ AUC เท่าไร → เกณฑ์ว่าผลจริง "เหนือบังเอิญ" หรือไม่
- คาดว่าผลจะออกมาถ่อมตัวอีกครั้ง — **ถ้าเป็นแบบนั้นต้องรายงานตรง ๆ** เหมือนที่ทำในบทที่แล้ว ห้ามปรับ threshold จนได้เลขสวย

### เกณฑ์เสร็จ
อ่านจบแล้วรู้ว่าเมื่อไรควรใช้ logistic แทนกฎ · อ่าน calibration curve เป็น · รู้ว่า AUC สูงแต่ calibration พังแปลว่าอะไร

## งาน I — rolling & expanding-window OLS

**ตัวเลือก:** เพิ่มเป็นหัวข้อใน `math-part8.html` บทที่ 6 (ที่สอน OLS อยู่แล้ว) หรือแยกเป็นบทเสริม `statarb-rolling-beta.html`

### ปัญหาที่จะแก้
คลังกระโดดจาก "OLS ครั้งเดียวบนข้อมูลทั้งชุด" (`math-part8`) ไป "Kalman filter ปรับ hedge ratio ตลอดเวลา" (`arb-part5` §19.2) โดยไม่มีขั้นกลาง — ซึ่งขั้นกลางนั่นแหละคือสิ่งที่คนทำงานจริงใช้มากที่สุด

### โครง
1. hedge ratio ที่คำนวณครั้งเดียวใช้ได้นานแค่ไหน — **วัดจากข้อมูลจริง** ว่า β ขยับไปเท่าไรใน 57 วัน
2. rolling window vs expanding window — เลือกยังไง เสียอะไร
3. ขนาดหน้าต่าง: สั้น = ไวแต่กระตุก · ยาว = นิ่งแต่ตามไม่ทัน · **ค่าปรับจากการค้นหาขนาดหน้าต่าง** (ใช้เครื่องจักรเดิมจาก Part 8 อีกครั้ง)
4. ทำไม Kalman ถึงเป็นคำตอบที่ "ถูกต้อง" กว่า และทำไมคนส่วนใหญ่ยังใช้ rolling อยู่ดี → ส่งต่อ `arb-part5` §19.2

### เกณฑ์เสร็จ
สะพานระหว่าง `math-part8` กับ `arb-part5` เดินได้ · ตัวเลข β drift มาจากข้อมูลจริง
