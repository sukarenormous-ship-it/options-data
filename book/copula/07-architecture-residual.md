# บทที่ 7 — residual มาจากไหน: สถาปัตยกรรม StatArb

> **บทนี้ตอบ:** ก่อนจะเอา copula ไปทำสัญญาณ ต้องเอาไปใส่ตรงไหนของระบบ
> และทำไม "ข้อมูลที่ป้อนเข้า copula" ถึงสำคัญกว่าตัว copula เอง
>
> สามบทถัดไปทำงานบน **residual** ทั้งหมด บทนี้คือบทที่บอกว่า residual คืออะไร
> ได้มาอย่างไร และถ้าข้ามขั้นนี้ไป สัญญาณที่คุณได้จะกลายเป็นอะไรแทน

---

## 7.1 ความเข้าใจผิดที่ต้องทิ้งก่อน

คำถามที่คนส่วนใหญ่เริ่มต้นคือ **"โมเดลไหนดีที่สุดสำหรับ StatArb"**

คำถามนี้ผิดตั้งแต่ต้น เพราะ StatArb **ไม่ใช่โมเดลตัวเดียว มันคือสถาปัตยกรรม**

โมเดลแต่ละชนิดตอบคนละคำถาม และคุณต้องการคำตอบของทุกคำถาม:

| องค์ประกอบ | คำถามที่มันตอบ |
|---|---|
| **Factor Model** | อะไรคือการเคลื่อนไหวร่วม |
| **Cointegration / OU / AR** | อะไรมีดุลยภาพหรือแนวโน้มจะกลับ |
| **Copula** | สถานะร่วมตอนนี้ผิดปกติไหม |
| **Portfolio Optimizer** | ควรถืออะไรเท่าไร |
| **Risk Model** | ที่ดูเหมือนกระจาย จริง ๆ เกี่ยวกันแค่ไหน โดยเฉพาะที่ tail |
| **Execution** | edge ที่เห็นเหลือเงินจริงหลังต้นทุนไหม |

การถามว่า "OU ดีกว่า copula ไหม" เหมือนถามว่า "เครื่องยนต์ดีกว่าเบรกไหม"
มันคนละหน้าที่

---

## 7.2 สถาปัตยกรรมที่แนะนำ

```
                  ┌─────────────────────┐
                  │   Market Returns    │
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │ Common Factor Model │   PCA / BTC beta / sector
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │      Residuals      │   ← ทุกอย่างหลังจากนี้ทำบน residual
                  └──────────┬──────────┘
                             ↓
              ┌──────────────┴──────────────┐
              ↓                             ↓
    ┌───────────────────┐         ┌───────────────────┐
    │   ALPHA           │         │  CONTEXT / RISK   │
    │  z-score / OU /   │         │      Copula       │
    │  ranking          │         │  conditional +    │
    │                   │         │  tail dependence  │
    └─────────┬─────────┘         └─────────┬─────────┘
              └──────────────┬──────────────┘
                             ↓
                  ┌─────────────────────┐
                  │  Portfolio Sizing   │
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │   Neutralization    │   factor / beta / sector
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │ Execution + Costs   │
                  └──────────┬──────────┘
                             ↓
                  ╔═════════════════════╗
                  ║    NET OOS P&L      ║   ← ลูกศรนี้สำคัญที่สุด
                  ╚═════════════════════╝
```

**ลูกศรสุดท้ายคือลูกศรที่ตัดสินทุกอย่าง** ไม่ว่า PCA, OU, cointegration
หรือ copula จะสวยทางคณิตศาสตร์แค่ไหน ถ้า

```
Net OOS Edge ≤ 0
```

มันยังไม่ใช่ trading edge

## 7.3 ทำไมต้องหัก common factor ก่อน — เหตุผลเชิงตัวเลข

นี่คือขั้นตอนที่คนข้ามบ่อยที่สุดและเสียหายมากที่สุดในคริปโต

**ถ้าไม่หัก:** สิ่งที่คุณคิดว่าเป็นสัญญาณ relative value ส่วนใหญ่คือ
"altcoin beta" ปลอมตัวมา 20 คู่ที่คุณถือคือเดิมพันเดียวกัน 20 ครั้ง
(บทที่ 10)

**ตัวเลขจริงในคริปโต:**

```
สัดส่วนความแปรปรวนที่อธิบายได้ด้วย PC1  ≈  60–80%
```

แปลว่า **ข้อมูลส่วนใหญ่ที่คุณเห็นคือตลาด ไม่ใช่สินทรัพย์**
ถ้าไม่หักออก คุณกำลังโมเดลตลาดซ้ำ 20 ครั้ง

**หักอย่างไร — สามทางเลือก เรียงตามความซับซ้อน**

```
1. BTC beta        e_i = r_i − β_i · r_BTC
2. PCA k factor    e_i = r_i − Σ β_ik · f_k
3. Sector + market  ซับซ้อนกว่า สำหรับ universe ใหญ่
```

ทางที่ 1 ง่ายที่สุดและใช้ได้ดีน่าประหลาดใจในคริปโต เพราะ BTC เป็น
factor ที่ครอบงำจริง ๆ **เริ่มจากอันนี้**

**ประเด็นที่ต้องระวัง:** `β` ต้องประมาณจากข้อมูลอดีตเท่านั้น (rolling)
และ `β` ในคริปโตไม่นิ่ง — ควร plot มันตามเวลาก่อนใช้

## 7.4 ตัวเลขที่ทำให้เห็นภาพ: ก่อนและหลังหัก factor

ในคริปโต **ทุกอย่างสัมพันธ์กับ BTC** ดังนั้น correlation ที่วัดได้ระหว่าง
ETH กับ SOL ส่วนใหญ่เป็นภาพลวง — มันคือ "ทั้งคู่ตาม BTC"

คำถามที่มีมูลค่าจริงคือ:

```
corr(ETH, SOL)        = 0.85     ← เกือบทั้งหมดคือ BTC beta
corr(ETH, SOL | BTC)  = 0.20     ← นี่คือความสัมพันธ์เฉพาะที่เหลืออยู่จริง
```

ตัวเลขหลังคือสิ่งที่คุณกำลังเทรดจริง ๆ ถ้าคุณทำ market-neutral
เพราะขา BTC beta ถูก hedge ออกไปแล้ว

**วิธีได้ตัวเลขหลังมามีสองทาง** — ทางง่ายคือ regress ทั้งคู่บน BTC
แล้วดู correlation ของ residual (ซึ่งคือสิ่งที่บทนี้สอน) ส่วนทางที่
ถูกต้องกว่าเชิงทฤษฎีคือ vine copula ซึ่งตอบได้ทั้ง correlation
และ tail dependence แบบมีเงื่อนไข แต่ซับซ้อนกว่ามาก
(ดู [ภาคผนวก D](appendix-d-vine.md) ถ้าสนใจ — สำหรับพอร์ตส่วนใหญ่
ทางง่ายให้คำตอบ 90% ด้วยความซับซ้อน 10%)

## 7.5 สิ่งที่ควรจำจากบทนี้

**สามบรรทัดสรุป**

1. StatArb เป็นสถาปัตยกรรม ไม่ใช่โมเดล — แต่ละชั้นตอบคนละคำถาม
2. ในคริปโตต้องหัก common factor ก่อนเสมอ (PC1 อธิบาย 60–80% ของความแปรปรวน)
   ไม่ใช่ทางเลือก แต่เป็นขั้นบังคับ
3. ทุกอย่างในสามบทถัดไปทำงานบน residual — ถ้าข้ามบทนี้ สัญญาณที่ได้
   จะเป็น "BTC beta ปลอมตัวมา" ไม่ใช่ relative value

## แบบฝึกหัด

**7.1** ทำ PCA กับ return รายวันของเหรียญที่คุณมีข้อมูล PC1 อธิบาย
ความแปรปรวนกี่เปอร์เซ็นต์ แล้วดู loading — มันคือ "ตลาด" จริงไหม
(ข้อมูลในรีโปมีสองเหรียญ ซึ่งน้อยเกินกว่าจะทำ PCA ให้มีความหมาย —
ข้อนี้ต้องดึงข้อมูลเพิ่มอย่างน้อย 8–10 เหรียญ)

**7.2** คำนวณ `corr(ETH, SOL)` และ `corr(ETH, SOL | BTC)` จากข้อมูลจริง
(อย่างหลังทำได้ด้วย partial correlation) ตัวเลขต่างกันเท่าไร
คุณคิดว่าคุณกำลังเทรดตัวไหน

**7.3** เทียบสัญญาณเดียวกันที่คำนวณจาก raw return กับจาก residual
จำนวนสัญญาณต่างกันแค่ไหน และสัญญาณที่หายไปตอนใช้ residual คือคู่แบบไหน

**7.4** plot `β` ของ ETH ต่อ BTC แบบ rolling 90 วัน มันนิ่งไหม
ถ้าไม่นิ่ง การใช้ β ตัวเดียวทั้งช่วงจะทำให้ residual ผิดไปแค่ไหน
