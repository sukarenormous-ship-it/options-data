# บทที่ 11 — copula ควรอยู่ตรงไหนในระบบ

> **บทนี้ตอบ:** บทที่ 7 วางโครงระบบไว้แล้ว บทที่ 8–10 บอกว่า copula ทำอะไรได้
> และทำอะไรไม่ได้ บทนี้เอาสองอย่างมาต่อกัน — copula ควรเสียบเข้าที่ช่องไหน
> และรวมกับสัญญาณอื่นอย่างไร

---

## 11.1 ทำไม copula ควรอยู่ในสาย "context" ไม่ใช่สาย "alpha"

จากบทที่ 9 เรารู้แล้วว่า copula ไม่บรรจุข้อมูลเรื่องเวลา
ดังนั้นการวางมันเป็นเครื่องกำเนิดสัญญาณหลักคือการขอให้มันทำสิ่งที่
มันทำไม่ได้โดยโครงสร้าง

การวางที่ถูกต้องคือให้มันตอบสิ่งที่โมเดล alpha ตอบไม่ได้:

| คำถาม | ใครตอบ |
|---|---|
| residual นี้เบี่ยงจากค่าเฉลี่ยกี่ sigma | z-score |
| มันมีแนวโน้มกลับไหม เร็วแค่ไหน | OU / AR |
| **สถานะร่วมกับสินทรัพย์อื่นนี้ ผิดปกติจริงไหม** | **copula** |
| ถ้าเข้าคู่นี้ พอร์ตจะกระจุกตัวขึ้นไหม | **copula (tail)** |

**การรวมสัญญาณสองแบบมีสองรูปแบบที่ต่างกันมาก**

**รูปแบบ AND (ตัวยืนยัน)**
```
เข้าเมื่อ:  |z| > 2  AND  |MI| > D
```
กรองเข้ม เทรดน้อยลง คุณภาพต่อเทรดสูงขึ้น (ถ้าสองสัญญาณตอบคนละคำถามจริง)

**รูปแบบ OVERLAY (ปรับขนาด)**
```
size = f(z) · g(tail crowding จาก copula)
```
ไม่ตัดเทรด แต่ปรับขนาดตามความเสี่ยงที่ copula เห็น

รูปแบบที่สองมักให้ผลดีกว่าในทางปฏิบัติ เพราะไม่ลด breadth
(ซึ่งเราเพิ่งเห็นในบทที่ 10 ว่ามีน้อยอยู่แล้ว)

---

## 11.2 คำถามที่ต้องตอบได้ก่อนเพิ่มชั้นใด ๆ

ก่อนใส่ copula (หรืออะไรก็ตาม) เข้าไปในระบบ ต้องตอบสามข้อนี้ได้:

**1. ชั้นนี้ตอบคำถามอะไรที่ชั้นที่มีอยู่ตอบไม่ได้**
ถ้าตอบไม่ได้เป็นข้อความชัด ๆ อย่าใส่

**2. ถ้ามันช่วยจริง จะเห็นอะไรในข้อมูล**
เขียนคำทำนายออกมาก่อนรัน backtest เช่น "ถ้า copula ช่วยจริง
hit rate ของเทรดที่ผ่านตัวกรองควรสูงกว่าที่ไม่ผ่านอย่างน้อย 3 จุด"

**3. ถ้ามันไม่ช่วย จะรู้ได้อย่างไร**
ถ้าไม่มีผลลัพธ์ใดที่จะทำให้คุณเอามันออก แปลว่าคุณไม่ได้กำลังทดสอบอะไร

ข้อ 3 คือข้อที่คนละเลยมากที่สุด และเป็นเส้นแบ่งระหว่างการวิจัย
กับการหาเหตุผลสนับสนุนสิ่งที่อยากทำอยู่แล้ว

---

## 11.3 ลำดับการสร้างที่ผมแนะนำ

อย่าสร้างทั้งระบบพร้อมกัน สร้างทีละชั้นและวัดผลทุกชั้น

```
สัปดาห์ 1:  factor model + residual + z-score          →  วัด baseline
สัปดาห์ 2:  เพิ่ม OU / half-life filter                 →  วัดส่วนเพิ่ม
สัปดาห์ 3:  เพิ่มต้นทุนจริงและ execution delay          →  วัดว่ายังเหลือไหม
สัปดาห์ 4:  เพิ่ม copula เป็น context                   →  วัดส่วนเพิ่ม
สัปดาห์ 5:  เพิ่ม copula tail overlay ใน sizing         →  วัดส่วนเพิ่ม
```

**สังเกตว่าต้นทุนเข้ามาตั้งแต่สัปดาห์ 3 ไม่ใช่สัปดาห์สุดท้าย**
เพราะถ้า edge ตายด้วยต้นทุน คุณไม่ควรเสียเวลาสองสัปดาห์ถัดไปเลย

การจัดลำดับแบบนี้ยังให้ของแถมสำคัญ: คุณจะมีตัวเลข baseline ที่ชัดเจน
สำหรับตอบคำถามในบทที่ 12 ว่า **copula เพิ่มอะไร**

---

## 11.4 นิยาม StatArb ที่แม่นที่สุด

หลังจากรื้อทุกชิ้นส่วนแล้ว:

> **Statistical Arbitrage คือการหา relative mispricing หรือ predictable
> residual structure ด้วยแบบจำลองเชิงสถิติ จากนั้นสร้าง long-short portfolio
> ที่ลด common risk และอาศัยการเดิมพันจำนวนมากที่มี edge เล็ก ๆ
> โดยพิสูจน์ผลในระดับ net P&L แบบ out-of-sample**

สังเกตว่านิยามนี้**ไม่บังคับ**ว่าต้องมี:

- cointegration
- copula
- OU
- PCA
- pair trading

เครื่องมือเหล่านี้เป็นเพียงชิ้นส่วน สิ่งที่ขาดไม่ได้คือสามอย่าง:
**การลด common risk**, **จำนวนเดิมพันที่มากพอ**, และ
**การพิสูจน์ที่ระดับ net OOS**

---

## 11.5 สิ่งที่ควรจำจากบทนี้

**สามบรรทัดสรุป**

1. StatArb เป็นสถาปัตยกรรม ไม่ใช่โมเดล — แต่ละชั้นตอบคนละคำถาม
2. ในคริปโตต้องหัก common factor ก่อนเสมอ (PC1 อธิบาย 60–80% ของความแปรปรวน)
3. วาง copula ในสาย context/risk แล้วรวมแบบ overlay มักดีกว่าใช้เป็นตัวกรองแบบ AND
4. สร้างทีละชั้นและวัดผลทุกชั้น โดยเอาต้นทุนจริงเข้ามาตั้งแต่ชั้นที่สาม
   ไม่ใช่ชั้นสุดท้าย — ถ้า edge ตายด้วยต้นทุน จะได้ไม่เสียเวลากับชั้นที่เหลือ
